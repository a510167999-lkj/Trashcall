# Trashcall「策略设置失败」修复与全项目代码审计报告

日期：2026-09-09 ｜ 范围：策略设置链路修复 + 全项目审计

> 说明：本项目为纯原生 iOS 应用（SwiftUI + CallKit CXCallDirectoryProvider + 共享 SQLite），不存在 Web/浏览器端代码。用户描述中的"移动端各主流浏览器"按"各主流 iOS 机型与系统版本（iOS 17 ~ 26/27）"理解并处理。

## 一、Bug 根因分析与修复

### 现象
真机上切换「一键防御策略」开关时弹出 **"策略设置失败: ..."**；批量切换报"批量策略设置失败"。

### 根因（复合因素，按因果链排序）

1. **重试窗口与设备端加载时长严重不匹配（主因）**
   `reloadExtension` 仅重试 3 次（0.8s/1.6s/2.4s，共约 4.8s）。当前种子库 **41 万条**识别记录，扩展流式注入在真机上远超此窗口。任何一次 reload 进行期间再次触发 reload，系统都会返回瞬态错误——`CurrentlyLoading (7)` 或 `LoadingInterrupted (2)`。重试耗尽后错误直接抛给 UI。
2. **UI 竞态放大（易复现的关键）**
   App 每次启动都会自动 reload 扩展；而策略开关在同步期间**没有禁用**（`isSyncing` 只禁用了"添加规则"按钮）。用户打开 App 后立刻拨动策略开关，几乎必然撞上进样中的 reload → 失败。
3. **错误语义错误**
   策略写库与系统重载耦合在同一个 do/catch 中：重载失败被报成"策略设置失败"，但此时**策略其实已持久化成功**（随后 `refreshStatus` 还会把开关显示为已开启），造成"报失败但开关变了"的自相矛盾。
4. **扩展未启用时的必然失败**
   扩展未在 系统设置→电话→通话阻止与身份识别 中开启时，`reloadExtension` 必然抛 `ExtensionDisabled (6)`，UI 仍一律报"策略设置失败"。
5. **次因（本轮一并硬化）**
   - SQLite 未设置 `busy_timeout`：App 与扩展跨进程竞争时，`BEGIN EXCLUSIVE` 立即返回 SQLITE_BUSY（"database is locked"）。
   - Toggle Binding 的 `get` 捕获了渲染时的旧值（`get: { isBlocked }`），状态可能不同步。

### 修复内容（3 个文件，+82/-27 行）

| 文件 | 修改 |
| --- | --- |
| `Sources/Trashcall/CallKitBridge/CallDirectoryManagerService.swift` | 重试升级：指数退避（0.6s→1.2s→2.4s→封顶 4s）最多 10 次，总窗口约 40s，覆盖真机 41 万条加载耗时；新增 `isTransientLoadingError` 同时识别错误码 2 与 7；保留 `isCurrentlyLoading` 兼容别名 |
| `Sources/Trashcall/Storage/CallDirectoryStore.swift` | `open()` 设置 `sqlite3_busy_timeout(3s)`，跨进程竞争时等待而非立即失败；`convertBlockingToIdentification` 对 label 做单引号转义 |
| `Sources/Trashcall/UI/TrashcallDashboardView.swift` | ① 策略开关与批量菜单在同步期间禁用；② 绑定 `get` 实时读取 + 乐观更新（写库失败由 refreshStatus 纠正）；③ 新增 `finishChangeAfterStoreWrite` 统一收尾：先查扩展状态，未启用则跳过重载并提示；重载失败区分为"设置已保存，但系统重载失败"；仍在加载则提示稍后手动同步。`addRule`/`deleteRules` 同步接入该语义 |

## 二、代码审计发现（按严重程度）

### 🔴 高优先级（建议尽快处理）

**A1. 策略关闭会"洗白"用户自定义黑名单，且 user_blocking_numbers 失同步**
`setStrategy(enabled: false)` 将命中号段的**所有** blocking 号码移回 identification（含用户通过自定义规则显式加入黑名单的号码），但不删除 `user_blocking_numbers` 中的对应行。后果：① 用户显式要求挂断的号码被静默恢复为"打标"；② UI 的"已写入系统底层库"徽标依赖 `user_blocking_numbers` 判断，产生假象。
建议：restore 时排除 `user_blocking_numbers` 中已有的号码，或在策略变更后重放全部用户规则。

**A2. Seed 导入失败仍写入版本号，造成静默数据缺失**
`DatabaseBootstrap.applyBundledSeedIfNeeded` 中若 `DELETE + 批量导入` 抛错，外层 `setupDatabase` 以 `catch { print }` 吞掉；但调用顺序上 `try store.setMetadata(key: "version", ...)` 在导入成功后才执行——真正的风险在于导入**部分成功**（buffer 批次中途失败回滚了事务，OK）与 `reapplyUserRules` 全程 `try?`：任何一步失败都无日志、无用户感知。
建议：引入 Logger/os_log 记录 bootstrap 每一步结果；导入失败时标记 dirty，下次启动强制重导。

**A3. 错误被静默吞掉的路径较多**
`getStore` 失败只报"无法连接离线数据库"，磁盘满 / App Group 失效 / 权限问题等根因全部不可见；`ExtensionRunReport.save`、`reapplyUserRules`、`migrateLegacyRootDatabaseIfNeeded` 均为 `try?`。
建议：统一错误日志通道（`Logger(subsystem: "com.trashcall.app", category: "storage")`），`getStore` 至少把底层错误带入 errorMessage。

### 🟡 中优先级

**B1. SQL 拼接面（脆弱模式，当前无实际注入）**
`setStrategy`/`setAllStrategies` 的 metadata 写入与 `restoreDefaultLabel` 使用字符串插值拼接 SQL；`queryCount`/`contains` 拼接表名。当前取值均为受控枚举常量，无注入风险，但属于易腐化模式（未来任何人加一个含引号的标签即出问题）。`convertBlockingToIdentification` 的外部 label 参数本轮已修复转义。建议全面改参数绑定。

**B2. 沙盒诊断的主线程开销**
`runDiagnosis` 绑定在 `onChange(of: diagnosticInput)`——每个键入字符都同步开库查询；命中通配符规则时会展开最多 5 万号码构建 `Set<Int64>`。数据量增长后有主线程卡顿风险。建议 300ms 防抖 + 移出主线程。

**B3. 主线程 SQLite 事务**
`toggleStrategy`/`addRule` 等的开库+事务都在 MainActor。当前数据量实测 <50ms 可接受，但库增长后应移入后台 Task。

**B4. WAL checkpoint 策略**
`checkpoint()` 使用 `SQLITE_CHECKPOINT_TRUNCATE` 且忽略返回值——扩展长时间流式读取期间 checkpoint 必然失败，WAL 文件可能持续膨胀。不影响正确性，建议改 PASSIVE 或定期全量 checkpoint。

**B5. MockContext 的 preconditionFailure**
`MockCallDirectoryContext` 在增量模式下重复条目直接 `preconditionFailure` 崩溃。该文件随 TrashcallCore 框架打进扩展包，虽然生产路径不使用，建议改 `assert`（Release 自动移除）或拆分到测试 target。

### 🟢 低优先级 / 安全

**C1. 剪贴板隐私体验**：`scenePhase == .active` 即读取 `UIPasteboard.general.string`，iOS 16+ 会触发系统"允许粘贴"弹窗。建议改用 `UIPasteboard.general.detectPatterns`（iOS 16+）在弹窗前判断，或仅用户主动操作后读取。

**C2. 数据供应链**：label 来自第三方 metowolf/vCards 仓库（构建期拉取）。构建脚本已有完整性校验（数量/长度/排序/排除名单）✓。建议 CI 固定该仓库 commit hash，防上游突变。

**C3. 数据安全**：黑名单为明文 SQLite 存于 App Group，内容仅为骚扰号段与标签，不含用户个人信息，风险可接受。

**C4. 权限最小化** ✓：App 与扩展 entitlements 均只声明同一 App Group，无多余权限。

**C5. 建议补充的测试**：策略关闭与用户规则冲突场景（对应 A1）；busy 竞争下的写入；`ExtensionRunReport` 损坏容错；`setStrategy` 关闭后 user_blocking_numbers 一致性。

### 本轮已顺手修复
- `sqlite3_busy_timeout` 跨进程竞争硬化（对应次因 5）
- `convertBlockingToIdentification` label 单引号转义（对应 B1 的一处真实风险点）

## 三、第二轮修复：「自动挂断」号码来电不被拦截（2026-09-09 补充）

### 现象
将自定义号码加入"自动挂断"列表后，该号码来电仍能正常打入；而"来电识别"打标一切正常。

### 根因
**iOS 26/27 会丢弃同一请求中与打标条目混提的 `addBlockingEntry`**。证据链：
1. 项目自身研究文档 `active/ios27-block-vs-identify/`：真机观察"识别能打标、自动挂断不行"，并引用 Apple DTS 论坛帖（developer.apple.com/forums/thread/800415）；
2. 代码内既有注释（`CallDirectoryFeedKind`）："iOS 26/27 ignores `addBlockingEntry` in an extension that also identifies callers"，且已预留 `identificationOnly`/`userBlockingOnly` 两种同质注入模式——**但生产扩展 `CallDirectoryHandler` 一直使用 `.full` 混发阻断+打标**，预留设计从未接入；
3. 混发请求下阻断条目被系统丢弃 → 挂断失效；打标条目不受影响 → 打标正常。与用户观察完全一致。
另有一类混合数据隐患会加剧此问题：seed 重导入可能让同一号码同时存在于 blocking 与 identification 两张表（`DatabaseBootstrap.applyBundledSeedIfNeeded` 只清 identification、不查 blocking 冲突）。

### 修复方案（专责双扩展架构）
| 变更 | 说明 |
| --- | --- |
| 新增 `CallDirectoryFeedKind.blockingOnly` | 只流式提交 `blocking_numbers`（含用户规则+策略划入的号码），无任何打标条目 |
| 新增挂断扩展 target `TrashcallBlockDirectory` | bundle id `com.trashcall.app.BlockDirectoryExtension`，principal class `CallDirectoryBlockHandler`，`feedKind = .blockingOnly`，运行报告 `extension_last_run_block.json`，同 App Group；已通过 xcodegen 重新生成工程 |
| 识别扩展切为 `.identificationOnly` | 不再混发阻断条目（其旧索引中的阻断条目会在下次全量请求时被系统自动清空） |
| `TrashcallExtensionID.blocking` + Dashboard 双扩展管理 | `reloadEnabledExtensions()` 同时重载已启用的识别/挂断扩展；hero 卡聚合状态——仅开识别时会提示"还需开启「Trashcall 挂断」开关"；高级设置新增挂断扩展同步统计与未同步告警 |
| `DatabaseBootstrap` 互斥清理 | seed 导入与策略重放后执行 `DELETE FROM identification_numbers WHERE phone_number IN (SELECT ...)`，保证两表永不相交 |
| App Intents 修正 | 快捷指令加黑名单后重载两个扩展（此前只重载识别扩展，挂断永不生效） |
| 版本 | 1.1.2 (11)，识别扩展显示名 "Trashcall 识别"、挂断扩展 "Trashcall 挂断" |

验证套件：新增"同质注入"测试（`.blockingOnly` 与 `.identificationOnly` 各自绝不混发），**14/14 全部通过**。

### 真机验证指南（修复是否生效）
1. **安装与开关**：Xcode 重新 Run（版本应为 1.1.2 (11)）→ 打开 设置 → 电话 → 通话阻止与身份识别 → **同时开启「Trashcall 识别」与「Trashcall 挂断」两个开关**（新扩展默认关闭，不开则挂断不生效——App 首页会给出对应提示）。
2. **App 内确认**：打开 Trashcall → 顶部应为"系统全能防护中"；添加测试号 `18964046784` 为自动挂断 → 高级设置中"挂断扩展上次同步统计"应显示 `注入自动挂断 ≥ 2 条` 且无扩展错误（2 条 = 86 前缀与裸号双形式）。
3. **清空豁免条件（关键，来自 Apple DTS 确认的 iOS 26/27 例外）**：
   - 若本机曾**拨打过**测试号：先在「电话 → 最近通话」中左滑**删除该去电记录**，否则系统永久豁免拦截；
   - 若测试号在**通讯录**中：先移除或改名，通讯录号码绝不拦截。
4. **来电实测**：用另一部手机拨打测试号 → 预期：**不响铃、直接静默挂断**，通话记录中出现"由 Trashcall 阻止"的拦截记录（iOS 26 起被拦来电会进未接列表并标注拦截 App，这不是失败）。
5. **反证**：将同一号码改为"来电识别"→ 再拨打 → 预期正常响铃但显示标记；再改回自动挂断 → 恢复拦截。同时用普通联系人来电验证**正常来电不受影响**（通讯录豁免本就优先）。
6. **若第 2 步统计为 0 或有扩展错误**：点「重新同步全量数据库」查看错误信息；挂断扩展内存上限 ~15MB/30s，挂断索引远小于打标库，正常秒级完成。

## 四、结论

1. "策略设置失败"的本质是：**策略早已写库成功，但系统重载（reloadExtension）在 41 万条数据的加载窗口内频繁失败，且被错误地报成了策略设置失败**。修复后：重试窗口扩大约 8 倍并覆盖两种瞬态错误码、同步期间 UI 防抖、扩展未启用时不再发起必然失败的重载、重载失败与设置失败语义分离。核心验证套件通过。
2. "自动挂断不生效"的本质是：**iOS 26/27 丢弃混发请求中的阻断条目**，而生产扩展一直用 `.full` 混发。修复后阻断与打标由两个专责扩展各自同质注入，从架构上消除该平台限制；配套修复 seed 重导入的两表重叠隐患与快捷指令只重载单扩展的遗漏。验证套件 14/14 通过。
